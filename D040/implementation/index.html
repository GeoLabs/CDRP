    Technical Implementation

    CCO provides a broader and more general ontology for modeling entities, processes, qualities, and relationships, making it suitable for semantic interoperability across domains.

    EDR is narrower and focuses specifically on environmental data retrieval through APIs, with concepts.

    Table 1 below provides a mapping between CCO and OGC EDR showing the BroderThan, NarrowerThan and similar concepts

    Table 1. Comprehensive Mapping between CCO and OGC EDR

    Category CCO Concept/Property EDR Concept/Property Relationship Remarks
    Core Entities
    Object cco:Object Not explicitly modeled Broader in CCO CCO models physical and abstract objects.
    Physical Object cco:PhysicalObject Not explicitly modeled Broader in CCO CCO models tangible entities.
    Process cco:Process Not explicitly modeled Broader in CCO CCO models activities or events.
    Event cco:Event Not explicitly modeled Broader in CCO CCO models specific occurrences.
    Quality cco:Quality Not explicitly modeled Broader in CCO CCO models attributes or properties of entities.
    Location cco:Location edr:Location Similar Both model spatial regions or places.
    Spatial Region cco:SpatialRegion edr:SpatialExtent Similar Both model spatial areas.
    Temporal Region cco:TemporalRegion edr:TemporalExtent Similar Both model time intervals.
    Parameter cco:Parameter edr:Parameter Similar Both model measurable properties.
    Information Object cco:InformationObject Not explicitly modeled Broader in CCO CCO models data or representations.
    Dataset cco:Dataset edr:Dataset Similar Both model collections of data.
    Measurement cco:Measurement Not explicitly modeled Broader in CCO CCO models quantified observations.
    Data Query Not explicitly modeled edr:DataQuery Narrower in EDR EDR focuses on data retrieval requests.
    Properties/Relationships
    hasQuality cco:hasQuality Not explicitly modeled Broader in CCO CCO links entities to their qualities.
    locatedIn cco:locatedIn edr:hasLocation Similar Both link entities to locations.
    participatesIn cco:participatesIn Not explicitly modeled Broader in CCO CCO links entities to processes.
    hasParameter cco:hasParameter edr:hasParameter Similar Both link processes or queries to parameters.
    hasPart cco:hasPart Not explicitly modeled Broader in CCO CCO links entities to their components.
    hasTemporalRegion cco:hasTemporalRegion edr:hasTemporalExtent Similar Both link entities to time intervals.
    hasValue cco:hasValue edr:hasValue Similar Both link measurements or parameters to values.
    hasUnit cco:hasUnit edr:hasUnit Similar Both link measurements or parameters to units.
    hasOutput cco:hasOutput Not explicitly modeled Broader in CCO CCO links processes to their results.
    Spatial/Temporal Types
    Point cco:Point edr:Point Similar Both model point geometries.
    Line cco:Line edr:Line Similar Both model line geometries.
    Polygon cco:Polygon edr:Polygon Similar Both model polygon geometries.
    Instant cco:Instant Not explicitly modeled Broader in CCO CCO models specific points in time.
    Interval cco:Interval Not explicitly modeled Broader in CCO CCO models time intervals with start and end points.
    Data and Measurements
    Information Object cco:InformationObject Not explicitly modeled Broader in CCO CCO models data or representations.
    Measurement cco:Measurement Not explicitly modeled Broader in CCO CCO models quantified observations.
    Dataset cco:Dataset edr:Dataset Similar Both model collections of data.
    Data Query Not explicitly modeled edr:DataQuery Narrower in EDR EDR focuses on data retrieval requests.
    Qualities and Parameters
    Quality cco:Quality Not explicitly modeled Broader in CCO CCO models attributes or properties of entities.
    Parameter cco:Parameter edr:Parameter Similar Both model measurable properties.

    Link/Bridge Concepts

    The Link/bridge concepts in the shared ontology are used to align and integrate the Common Core Ontologies (CCO) and the OGC Environmental Data Retrieval (EDR). These bridge concepts ensure that the two ontologies can be interoperable. Table 2 below shows the bridge relationships between CCO and EDR.

    Table 2: Bridge concepts between CCO and EDR

    Bridge Concept CCO Concept OGC EDR Concept Remarks
    EnvironmentalData cco:InformationContentEntity edr:EnvironmentalData Represents environmental data.
    Sensor cco:Device edr:Sensor Represents a device that measures environmental data.
    Observation cco:Process edr:Observation Represents the act of observing environmental data.
    FeatureOfInterest cco:Object edr:FeatureOfInterest Represents the entity being observed.
    Measurement cco:QualityValue edr:Measurement Represents a quantitative value of an observation.
    Location cco:SpatialLocation edr:Location Represents a spatial location.
    Time cco:TemporalLocation edr:Time Represents a temporal location.
    hasLocation cco:hasSpatialLocation edr:hasLocation Links an entity to its spatial location.
    hasTime cco:hasTemporalLocation edr:hasTime Links an entity to its temporal location.
    observes cco:performs edr:observes Links a sensor to the observation it performs.

    Using the bridge concepts and the concept mappings described above the shared ontology is shown below.

    Shared Ontology (ccoedr):

         xmlns:rdfs="http://www.w3.org/2000/01/rdf-schema#"
         xmlns:cco="http://www.ontologyrepository.com/CommonCoreOntologies/"
         xmlns:edr="http://www.opengis.net/ont/edr#"
         xmlns:ccoedr="http://www.example.org/ccoedr#">

  <!-- Shared Classes -->
  <owl:Class rdf:about="ccoedr;SpatialRegion">
    <rdfs:subClassOf rdf:resource="cco;SpatialRegion"/>

  <!-- Axioms for Reasoning -->
  <owl:ObjectProperty rdf:about="ccoedr;hasOutput">
    <owl:propertyChainAxiom rdf:parseType="Collection">
      <rdf:Description rdf:about="ccoedr;hasOutput"/>
      <rdf:Description rdf:about="ccoedr;retrieves"/>
    </owl:propertyChainAxiom>
  </owl:ObjectProperty>

  <owl:ObjectProperty rdf:about="ccoedr;measures">
    <owl:inverseOf rdf:resource="ccoedr;hasParameter"/>
  </owl:ObjectProperty>

  <owl:ObjectProperty rdf:about="ccoedr;hasParameter">
    <owl:propertyChainAxiom rdf:parseType="Collection">
      <rdf:Description rdf:about="ccoedr;hasParameter"/>
      <rdf:Description rdf:about="ccoedr;measures"/>
    </owl:propertyChainAxiom>
  </owl:ObjectProperty>

  <owl:ObjectProperty rdf:about="ccoedr;retrieves">
    <owl:inverseOf rdf:resource="ccoedr;hasOutput"/>
  </owl:ObjectProperty>

</rdf:RDF>

    SHACL Schema for the Shared Ontology

    @prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix cco: <http://www.ontologyrepository.com/CommonCoreOntologies/> .
@prefix edr: <http://www.opengis.net/ont/edr#> .
@prefix ccoedr: <http://www.example.org/ccoedr#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

    Shape for Location

    ccoedr:LocationShape
    a sh:NodeShape ;
    sh:targetClass ccoedr:Location ;
    sh:property [
        sh:path rdfs:label ;
        sh:datatype xsd:string ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
    ] ;
    sh:property [
        sh:path ccoedr:SpatialRegion ;
        sh:class ccoedr:SpatialRegion ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
    ] .

    The above SHACL schema defines constraints and validation rules to ensure that the data conforms to the structure and relationships defined in the CCO-EDR shared ontology.

    Semantically Annotated OGC EDR Example Data using the Shared Ontology in JSON-LD

    {
  "@context": {
    "ccoedr": "http://www.example.org/ccoedr#",
    "edr": "http://www.opengis.net/ont/edr#",
    "rdfs": "http://www.w3.org/2000/01/rdf-schema#",
    "xsd": "http://www.w3.org/2001/XMLSchema#"
  },
  "@id": "http://example.org/data#RainfallDataset_2020",
  "@type": "ccoedr:Dataset",
  "rdfs:label": "Rainfall Dataset 2020",
  "ccoedr:hasParameter": {
    "@id": "http://example.org/parameter#Rainfall",
    "@type": "ccoedr:Parameter",
    "rdfs:label": "Rainfall",
    "ccoedr:hasUnit": "millimeters"
  },
  "ccoedr:hasTemporalExtent": {
    "@id": "http://example.org/time#Interval_2020",
    "@type": "ccoedr:TemporalRegion",
    "rdfs:label": "October 1-7, 2020",
    "ccoedr:hasStartTime": { "@value": "2020-10-01T00:00:00Z", "@type": "xsd:dateTime" },
    "ccoedr:hasEndTime": { "@value": "2020-10-07T23:59:59Z", "@type": "xsd:dateTime" }
  },
  "ccoedr:hasLocation": {
    "@id": "http://example.org/location#XYZLocation",
    "@type": "ccoedr:Location",
    "rdfs:label": "XYZ location",
    "ccoedr:SpatialRegion": {
      "@id": "http://example.org/spatial#Region_XYZLocation",
      "@type": "ccoedr:SpatialRegion",
      "rdfs:label": "Spatial Region of XYZ location"
    }
  },
  "edr:data": [
    {
      "@type": "edr:DataPoint",
      "edr:time": { "@value": "2020-10-01T12:00:00Z", "@type": "xsd:dateTime" },
      "edr:value": 13.2
    },
    {
      "@type": "edr:DataPoint",
      "edr:time": { "@value": "2020-10-02T12:00:00Z", "@type": "xsd:dateTime" },
      "edr:value": 16.5
    },
    {
      "@type": "edr:DataPoint",
      "edr:time": { "@value": "2020-10-03T12:00:00Z", "@type": "xsd:dateTime" },
      "edr:value": 10.7
    }
  ]
}

    The above JSON-LD document represents a semantically annotated dataset using the Shared Ontology. It includes metadata such as temporal extent, location, and associated parameters while conforming to the OGC Environmental Data Retrieval (EDR) standard.
